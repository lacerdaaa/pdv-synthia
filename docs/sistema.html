Fatos imutáveis

Um dono por dado

Vendas nascem no caixa; catálogo, preço e estoque de entrada, na retaguarda. Quase nenhum conflito.

Reenviar é seguro

Todo evento tem ID único gerado na origem. O servidor ignora repetidos: entrega pelo menos uma vez, sem duplicar.

Infraestrutura e código

Uma linguagem do caixa à nuvem

Tudo em C# / .NET 10. Os contratos (formato dos eventos e mensagens) são um projeto só, usado pelo caixa e pelo servidor.

Synthia.ContractsEnvelope de evento, payloads (venda, turno, entrada, contagem, perda, NFC-e), mensagens de sync, UUIDv7 monotônico.
Synthia.Terminal.CoreCoração do caixa: SQLite local, outbox, catálogo, carrinho, sessão de checkout, turno, cupom, chave e numeração de NFC-e, workers de sync.
Synthia.Terminal.DevicesBalança Toledo (serial), impressora ESC/POS (rede, serial, USB), leitor serial, versões simuladas de tudo.
Synthia.Terminal.AppTela do caixa em Avalonia: operação 100% pelo teclado, com a marca do Xandão.
Synthia.ServerASP.NET Core + PostgreSQL: API de sync, log de eventos, projeções (estoque, turnos, fila de NFC-e), OpenAPI e /docs.
Retaguarda (Blazor)Back-office no navegador: produtos, entradas, notas XML, estoque, inventário, perdas, NFC-e, vendas, fechamentos, usuários.
tests/ + tools/169 testes (caixa, servidor com Postgres real, tela do caixa sem monitor), simulador de um dia de loja.

Na loja

Servidor local

Mini PC com PostgreSQL e o Synthia.Server. Também é o relógio (NTP) dos caixas. Backup diário.

Rede

VLAN só dos caixas; roteador com fibra + 4G de reserva. Nenhuma porta aberta para fora.

Energia

No-break segurando caixas, rede e servidor por alguns minutos; desligamento limpo se passar.

Nuvem (fase 2)

Cópia dos eventos, backup e XMLs das NFC-e por 5 anos. A loja nunca depende dela.

Sincronização

Outbox, reenvio e idempotência

A venda e o evento são gravados na mesma transação do SQLite. Um worker envia em lotes; se a resposta se perde, ele reenvia e o servidor simplesmente ignora o repetido.

Caixa → servidor

A cada 2 s (ou logo após a venda): até 100 eventos, em ordem. Erro: espera 2 s, 4 s… até 60 s e tenta de novo.

Servidor → caixas

Catálogo versionado: cada alteração ganha um número. O caixa pede só o que mudou desde a versão dele; se ficou muito para trás, baixa tudo.

Preço agendado

Chega antes e o próprio caixa aplica no horário, mesmo offline. Todos mudam juntos.

ID na origem

UUIDv7 crescente: ninguém pede ID ao servidor e um cancelamento nunca fica antes da própria venda.

Estoque

O saldo é calculado, nunca digitado

Estoque = última contagem + movimentos depois dela. Cada linha é um fato vindo do caixa ou da retaguarda. Por isso dá para reconstruir tudo do zero e o inventário funciona com a loja aberta.

Retaguarda

O escritório da loja, no navegador

Servida pelo próprio servidor em /retaguarda, com login e papéis (admin, gerente, estoquista). Nome, logo, cores e rodapé do cupom de cada loja vêm do cadastro em Loja e chegam aos caixas pelo sync. As telas trocam sozinhas; clique para navegar.

Cenários de falha

O que acontece quando algo cai

Nenhuma falha isolada impede a venda em dinheiro. Escolha um cenário.

Segurança

Cada um entra pela sua porta

Caixas → sync

Cada caixa tem sua chave (X-Terminal-Key). Um caixa não consegue enviar eventos em nome de outro.

Pessoas → retaguarda

Usuário e senha (hash), papéis admin/gerente/estoquista. Desativou, perdeu o acesso na hora.

Integrações → API

Chave de API (X-Api-Key) ou o login da retaguarda. A API nunca é anônima.

Produção

Sem chaves configuradas, todo sync é recusado. Em desenvolvimento, aceita com aviso, para o modo demonstração.
